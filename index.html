Data identity

Massive-scale identity resolution

Problem A legacy HTTP/MongoDB platform struggled to scale as identity data grew, requiring recurring operational intervention and periodic reduction of historical data. Identity data arriving from multiple sources used inconsistent identifiers, making it difficult to maintain a stable and scalable identity layer as volume grew.

Architecture Re-architected the platform as a Spark-native data system using Apache Iceberg and EMR-on-EKS, orchestrated through Airflow. The system performs identity resolution against a 65B+ historical mapping dataset while processing 10B+ incoming device records daily, resolving one stable internal ID per device and writing refined Iceberg tables.

Key engineering decisions Optimized data layout and joins using Iceberg Storage Partition Joins with zero OOMs or disk spills; implemented controlled, deterministic and idempotent ID-resolution processing to prevent duplicate assignments; tracked first-seen/last-seen and opt-out/privacy state incrementally; and automated Iceberg metadata cleanup and compaction to control small-file fragmentation and maintain stable performance.

Outcome Reduced processing time from approximately 18–20 hours to around 60 minutes while eliminating recurring database outages and removing the need for periodic historical data truncation.
